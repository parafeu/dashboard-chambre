# v1.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Détection de mouvement OpenCV robuste, bandeau batterie + bouton Réglages, écran Réglages 2 colonnes avec aperçu, batterie envoyée à HA via Mobile App.

**Architecture:** Décision de mouvement en Kotlin pur (`MotionDecider`) alimentée par un analyseur OpenCV ; batterie lue par broadcast collant → `StateFlow<BatteryState>` → UI + `BatteryReporter` → `MobileAppClient` (REST HA).

**Tech Stack:** existant + `org.opencv:opencv:4.12.0`.

**Spec:** `docs/superpowers/specs/2026-10-16-v1.1-mouvement-reglages-batterie-design.md`

## Global Constraints
- minSdk 30 ; release ABI `armeabi-v7a` seul ; debug `armeabi-v7a` + `x86_64`.
- Seuil global 0.60 ; 2 images actives sur 3 ; aveuglement 2 s ; minArea défaut 0.03 (0.005–0.10).
- MOG2 history 150, varThreshold 25, pas d'ombres ; analyse 160×120 ; flou 5×5 ; ouverture 3×3.
- Batterie : envoi immédiat (1er état, changement charge), sinon ≥ 5 min si niveau/temp (±1 °C) change, renvoi 30 min ; 410 → réenregistrement.
- Device « Tablette chambre », app_id `fr.alex.chambre`.
- Ne jamais toucher le dashboard d'un appareil connecté au vrai HA pendant les tests.

## Review Focus
1. Pas de caméra / OpenCV qui ne se charge pas → veille au toucher, pas de crash.
2. HA injoignable ou jeton vide → BatteryReporter n'envoie rien, ne plante pas, réessaie plus tard.
3. Intégration supprimée dans HA (410) → réenregistrement automatique.
4. Température batterie absente (-1 / 0) → capteur température non envoyé plutôt qu'une valeur fausse.
5. Écran Réglages ouvert → pas de mise en veille, aperçu arrêté à la fermeture.
